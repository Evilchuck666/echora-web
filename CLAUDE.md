# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Echora Web is the browser client of Echora, a self-hosted music streaming service. It talks to the Echora API (Symfony + API Platform), which lives in a separate repository at `../Echora` (https://github.com/Evilchuck666/Echora). Native apps for other platforms are planned on the same API, so business rules belong in the API, not here.

## Commands

```sh
bun install          # install dependencies
bun run dev          # Vite dev server at http://localhost:5173
bun run build        # type check (tsc -b) and production build into dist/
bun run typecheck    # type check only
bun run lint         # oxlint
bun run test         # unit tests (Vitest); `bun test` would run Bun's own runner instead: always `bun run test`
bun run test:e2e     # end-to-end tests (Playwright) against the mock API
bun run test:e2e:live  # a few end-to-end tests against the real API (needs e2e/.env)
bun run preview      # serve the production build
bun run api:types    # regenerate src/api/schema.d.ts from the running API
```

## Tests

- **Unit** (Vitest + happy-dom, `src/**/*.test.ts`, setup in `src/test/`): logic without UI, above all the session (single-flight and cross-tab refresh, sign-out), the API client's middleware, and the player engine. `fetch` is a mock set before any import, because openapi-fetch keeps the fetch it finds when a client is created: configure it per test with the helpers in `src/test/http.ts` (`routes()`, `json()`, `calls()`, `jwt()`). happy-dom has no Web Locks (`navigator.locks` is `null`): `src/test/locks.ts` installs a shared stand-in.
- **End-to-end** (Playwright, `e2e/`): the app in Chromium (project `mocked`, autoplay allowed) and in Firefox (project `mocked-firefox`, with Firefox's own autoplay defaults: audio only after a click on the page; `autoplay-blocked.spec.ts` sets the click-to-play preferences of hardened setups, Firefox only). Firefox found a bug Chromium never showed (see `session.ts`): keep both green. Firefox plays audio only through a sound server (PulseAudio or PipeWire): the desktop's locally; CI starts PulseAudio, whose null sink is enough. Without one, every test that waits for the position to move fails in Firefox. `e2e/mocked/` runs against `e2e/support/mock-api.ts`, a stateful mock of the Echora API (login, single-use refresh tokens, library, search, a real WAV stream, SVG covers, injectable failures) installed with `context.route()` through the fixtures in `e2e/support/fixtures.ts`; it needs no server and runs in CI (`.github/workflows/ci.yaml`). `e2e/live/` runs against the real API and library, skipped unless `e2e/.env` sets `ECHORA_E2E_USERNAME` and `ECHORA_E2E_PASSWORD` (see `e2e/.env.example`); it must not depend on particular artists. Playwright starts its own Vite on port 5179.
- Locate elements by role and accessible name (`getByRole('region', { name: 'Player' })`), as users and screen readers find them: keep `aria-label`s meaningful. When a feature changes the API's behaviour the client relies on, update the mock API too.
- After a change, run `bun run lint`, `bun run build`, `bun run test` and `bun run test:e2e`.

## Layout

- `src/main.tsx`: mounts the providers (TanStack Query, React Router).
- `src/app/`: app-wide setup: `router.tsx` (routes), `query-client.ts` (also clears the cache on sign-out).
- `src/api/`: (`bun run api:types` passes `--default-non-nullable false`: otherwise openapi-typescript makes every field with a default required, also in request bodies, e.g. `position` in a merge patch that only renames) `client.ts` (the typed `openapi-fetch` client, its authentication middleware, and `unwrap()` to turn a call into data or an `ApiError` for `queryFn`; `unwrapEmpty()` for calls answered without a body, 204) and `schema.d.ts` (generated, committed so builds don't need the API; never edit it by hand).
- `src/auth/`: the session. `tokens.ts` keeps the tokens in `localStorage` (shared by every tab) and exposes `useSession` (Zustand); `session.ts` signs in and out and refreshes the JWT, single-flight within a tab and under a Web Lock across tabs, re-reading the tokens once the lock is held. After writing new tokens it lets the task end before releasing the lock: Firefox passes localStorage writes to other tabs at the end of a task, and another tab could otherwise get the lock and read the spent refresh token. Signing out takes the same lock, so it invalidates the current refresh token. `RequireAuth` guards the signed-in routes.
- `src/library/`: the music library: `queries.ts` (TanStack Query hooks for artists, albums, tracks (also every album and every track of the library: `useAlbums`, `useTracks`), the search and a track's lyrics; `fetchAllTracks()` loads every page of an album's or an artist's tracks, to queue them at once), `favourites.ts` (favourite tracks, albums and artists: `setFavourite()` changes the hearts at once and calls `PUT`/`DELETE /api/{kind}s/{id}/favourite`, putting them back with a toast if it fails; the changes made during the visit live in a small Zustand store that wins over the API's `favourite` field, so every heart on screen follows without refetching, and is cleared on sign-out; the favourites lists are only marked stale, so the one on screen keeps what was removed and it can be put back; `useFavouriteTracks/Albums/Artists`, `fetchAllFavouriteTracks`), `playlists.ts` (the user's playlists, in their own order (a new one first; `movePlaylist` moves one, shown at once, the moves sent one at a time like the item changes): `usePlaylists/usePlaylist/usePlaylistItems`, create, rename, delete, add tracks (several at once, at the end), move and remove items; the page shows a move or a removal at once (`moveInPages`), and the changes to a playlist reach the API one at a time, in order (`inOrder`): positions are indexes in the API's current order, so a removal overtaking a move made it land one place off; the items are read again once the last change is done; both PATCH requests are `application/merge-patch+json`), `types.ts` (aliases of the generated JSON-LD schemas), `format.ts` (durations, plurals).
- `src/components/`: shared components: `AppLayout` (the frame of signed-in pages, with `ScrollRestoration`; the header has a fixed height, `h-14`, which the player's column and the sidebar start below; from `lg` a sidebar at the left (`w-56`, the page pads for it), below it a menu button in the header opens `NavDrawer`), `Navigation` (the places of the app (Artists, Albums, Tracks, Favourites), and the user's playlists with "New playlist", each moved by dragging its handle (dnd-kit, also by touch and keyboard), in both), `Dialog` (an accessible modal in a portal: focus inside and back, Escape and a click outside close it, its keys don't reach what is behind), `PlaylistDialogs` (name a playlist; "Add to playlist": the user's playlists, read again when it opens, or a new one made there), `NavDrawer` (slides in from the left, closes on a choice, Escape, a click outside or a resize to `lg`, keeps the focus inside and returns it to the menu button), `FavouriteButton` (the heart: a toggle button, `aria-pressed`, named "Favourite {name}"), `TrackItem` (a track among others of various albums, with a heart and the "⋯" menu: search results and favourites; `ON_HOVER` is the class that shows row buttons on hover, focus or touch), `Cover` (album cover or placeholder), `ArtistImage` (round artist thumbnail or the initial), `LibraryCards` (`ArtistCard`, `AlbumCard`, typed by the fields they show so list and search results both fit; `AlbumCard` has a "⋯" queue menu over the cover and `ArtistCard` a heart over the thumbnail, both outside the card's link), `ActionsMenu` (the accessible "⋯" menu: arrows, Escape, rendered in a portal and kept on screen; also takes another icon, and choices as `menuitemradio` items with a description), `toast.ts` + `Toaster` (`showToast()`, a short confirmation in a live region), `SearchBox` (the header search, with a × button: navigates from its change handler after a pause, not from an effect, and follows the URL while rendering), `InfiniteScrollTrigger`, `QueryError`, `Spinner`, `Breadcrumbs`.
- `src/library/search.ts`: `searchUrl()` and `useLeaveSearch()`. An empty search URL (`/search`, `/search?q=`, a blank `q`) is never written nor shown: emptying the query goes back to the page the search started from (`navigate(-1)`), or replaces it with `/` when the app was opened on it (React Router's `history.state.idx` is 0).
- `src/player/`: the player. `store.ts` (Zustand: the queue as `{key, track}` entries, so a track can be queued twice, in playing order plus `unshuffled`, the order to restore when shuffle goes off; index, origin (e.g. `artist:{id}` for Play all), playing, time, volume, shuffle, repeat `off`/`all`/`one`; quality `original`/`data-saver` (default data saver on touch screens); volume, mute, shuffle, repeat and quality are persisted here, in `localStorage`), `saved-queue.ts` (the queue, its unshuffled order, the current track, the origin and the position, kept in `localStorage` under `echora.queue` without stream URLs (they expire; the engine fetches fresh ones), at most 1 000 tracks around the current one), `engine.ts` (two `Audio` elements, created outside React so music survives navigation: one plays, the other loads the next track during the last 30 s of the current one (renewing its URL first if needed; dropped if the queue changes), and they swap when it starts (the old element stays as it was until the new one plays: if the browser refuses to play the spare, as Safari may, it loads the track instead); a `NotAllowedError` (autoplay blocked, e.g. Firefox with autoplay set to block audio, where every `play()` needs a click) shows "Autoplay blocked: press Play" in the bar instead of stopping silently; only the playing element's events write the store, and its exported controls are the only way to drive it, queue operations included (`playQueue`, `playNext`, `addToQueue`, `jumpTo`, `removeFromQueue`, `moveInQueue`, `toggleShuffle`, `cycleRepeat`); Play next and Add to queue on an empty queue load the tracks paused; plays a track's `opusStreamUrl` with the data saver on (FLAC only; MP3 tracks have none, and browsers without Opus get the original), and `setQuality` switches the current track at its position and reloads the preload; renews an expiring or failed (401) `streamUrl` by fetching the track again, once; Media Session; one tab at a time: a `BroadcastChannel` (`echora.player`) tells the other tabs to pause when one starts playing; saves the queue a few seconds after it or the position changes, at once on pause and on `pagehide`, only when this tab changed something (an idle tab never overwrites another tab's save), and `restoreSavedQueue()` puts it back paused when it starts; stops and forgets the saved queue on sign-out; in development a change to it, or to a module it imports, reloads the whole page (`import.meta.hot.accept(() => location.reload())`: hot-swapped, the old engine would play on beside the new one; `hot.decline()` is a no-op in Vite)), `PlayerBar.tsx` (fixed bar, always shown in `AppLayout`, with the space and arrow shortcuts; with nothing queued, Play or space plays the whole library), `library.ts` (`playLibrary()`: starts with the first page of `/api/tracks`, or a random one with shuffle, and adds the other pages meanwhile through the engine's `extendQueue`, which places them at random after the current track with shuffle on, and stops once another queue plays; `playLibraryFrom()` starts from a track of the pages the Tracks page has loaded, then adds the next pages the same way), `PlayerPanel.tsx` (the frame of the panels opened from the bar), `usePanels.ts` (which panels are open and where: from `xl` a column at the right of the page, the queue above the lyrics, the queue open from the start, remembered in `localStorage`, and `AppLayout` pads the page for it (`useDockedColumn`); below, floating over the page, side by side from `lg`, one at a time on narrow screens, Escape closing the last one opened), `LyricsPanel.tsx` (follows the current track; fetches `GET /api/tracks/{id}` only when the list said `hasLyrics`), `QueuePanel.tsx` (what plays and what comes next, the first 100 upcoming tracks listed: jump, remove, reorder with dnd-kit by mouse, touch or keyboard, with announcements; "Save as playlist" makes a new playlist of the current track and the ones to come, in playing order, through `createPlaylistWithTracks`, which adds them 500 at a time), `QueueMenu.tsx` ("⋯" with Play next, Add to queue and Add to playlist, for tracks and albums), `QualityMenu.tsx` (Original or Data saver, next to the volume), `transcodes.ts` (with the data saver on, and a browser that plays Opus, sends the next tracks with an Opus version (at most 20, after the current one, each once, in order; from the top too when repeating the queue) to `POST /api/transcodes` 500 ms after the queue, the position, the repeat mode or the quality change, unless the list is the same as last time; an empty list once when there is nothing left to prepare; fire and forget, never retried; `deviceId()` is a UUID kept in `localStorage` as `echora.deviceId`, for good, whoever signs in; imported by the engine), `icons.tsx`. Components read the store and call the engine; never touch the audio elements elsewhere.
- `src/pages/`: one component per route: `/` artists, `/artists/:id` its albums, `/albums` every album (in the library's order, the API's: album artist by name, then year and title), `/albums/:id` its tracks, `/tracks` every track (in the library's order; Play plays the library, a track plays it from there with `playLibraryFrom`), `/search?q=` the global search (`GET /api/search`, `limit=50`, sections folded until "Show all"), `/favourites/artists`, `/favourites/albums` and `/favourites/tracks` (`FavouritesPage`, newest first; tracks with Play), with `/favourites` (the sidebar's link) redirecting to the tab shown last (`echora.favouritesTab` in `localStorage`; Artists the first time), `/playlists/:id` (`PlaylistPage`: cover mosaic, Play, rename and delete from its menu (deleting asks in a dialog), items to drag with dnd-kit and remove; 404 for a playlist that isn't the user's), `/login`.

Conventions:

- The `api` client is typed for `application/ld+json` (`createClient<paths, 'application/ld+json'>`), so responses have the JSON-LD shapes (`member`, `totalItems`, `view`). Wrap calls in `unwrap()` inside `queryFn`.
- Collections are infinite queries: `initialPageParam: 1` and `getNextPageParam: (page) => nextPage(page.view)`, with an `InfiniteScrollTrigger` after the list. Relation filters take IRIs (`/api/artists/{id}`).
- Show the page-level `QueryError` on `isLoadingError`, not `isError`: once data is on screen, a failed next page or refetch must not replace it (the trigger offers a retry instead). Server and network errors are retried twice automatically; 4xx aren't.
- `.env` sets `VITE_API_URL` (the API origin, without `/api`, since the generated paths include it). Local overrides go in `.env.local` (git-ignored). `.env.production` sets it empty: in production the app is served by the API's own Caddy on the same origin and calls `/api/...` by path. Never assume the API is on another origin (no absolute API URLs built in code; media URLs come absolute from the API).

## Production

Not deployed on its own: `../Echora`'s production image builds this repository (its `compose.prod.yaml` passes it as the `web` build context, `WEB_DIR`, and its Dockerfile runs `bun install --frozen-lockfile` and `bun run build`) and its Caddy serves `dist/` at the root of the site, falling back to `index.html` for the app's routes; `/api`, `/bundles` and `/.well-known` go to the API. So `bun run build` must keep working from a clean checkout, `dist/` must stay self-contained, and new top-level routes must not start with those prefixes. `.dockerignore` keeps `node_modules`, reports and `e2e/.env` out of that build context. `bun run preview` proxies `/api` to the local API. `ECHORA_E2E_BASE_URL` runs the live tests against a deployment. The API's CI (job "Production image") builds this repository's `main` into its production image and smoke-tests it: a change that breaks `bun install --frozen-lockfile` or `bun run build` there fails the API's CI too.

## Decided stack

- Vite + React + TypeScript, styled with Tailwind CSS 4 (through `@tailwindcss/vite`; no `tailwind.config`, configuration lives in CSS).
- **TypeScript 6, not 7**: TypeScript 7 (the native compiler) has no JavaScript API, which `openapi-typescript` needs, and the editor only supports it experimentally. Move to 7 when both do.
- Linting with **oxlint** (`.oxlintrc.json`), the current Vite template's default. No formatter has been chosen yet.
- **Bun** is the package manager and script runner (`bun install`, `bun run <script>`, `bunx`). Don't use npm, pnpm or yarn, and don't commit their lockfiles.
- TanStack Query for server state, React Router for routing, Zustand for client state (the player: queue, current track, volume).
- API types generated from the API's OpenAPI specification with `openapi-typescript`, and requests made with `openapi-fetch`. Don't hand-write API types: regenerate them when the API changes.
- The interface is in **English only**: no i18n library.
- Same stack as the author's other React project (ArchivAries), on purpose.

## The Echora API

The local API runs from `../Echora` with `docker compose up --wait` at **https://localhost/api** (Swagger UI there; OpenAPI at `/api/docs.jsonopenapi`). Its README and its `bruno/` collection document every endpoint, and `docs/decisions/` why it is built that way: when a change asked from this repository shapes the API (a new endpoint, a rule, how something is served), add a record there too, saying it came from echora-web. Rules the client must follow:

- **Collections need JSON-LD** (`Accept: application/ld+json`, the default): items are in `member`, the total in `totalItems`, and pagination links in `view` (`first`, `next`, `last`; 30 items per page, `page` query parameter). With `Accept: application/json` a collection is a bare array with no total or links.
- **Filters** take IRIs for relations: `/api/albums?artist=/api/artists/{id}`, `/api/tracks?album=/api/albums/{id}`. Text filters (`name`, `title`) are partial and case-insensitive. `/api/tracks?albumArtist=/api/artists/{id}` lists every track of an artist's own albums (`artist` filters by track artist). Default order: artists by name, albums in the order of the library (album artist by name, then year and title; by year and title for one artist), tracks in the order of the library (album artist by name, album by year and title, then disc and track number).
- **Authentication**: `POST /api/auth` with `{"username", "password"}` returns `{token, refresh_token, refresh_token_expiration}`. Send `Authorization: Bearer <token>` on every request. The JWT lasts one hour. `POST /api/token/refresh` with `{"refresh_token"}` returns a new pair.
- **Signing out**: `POST /api/logout` with `{"refresh_token"}` invalidates it (no JWT needed). The JWT stays valid until it expires, so drop it locally too.
- **Refresh tokens are single use with reuse detection**: presenting a refresh token that was already spent revokes the whole session, also when two requests present it at the same time (the API serializes them). One exception, the API's grace period: for 5 minutes after a refresh, the spent token still works as long as its successor is unused, so a refresh whose response was lost (reload, closed tab, network cut) doesn't sign the user out; the client keeps the old token on a network error and simply tries again. The mock API (`e2e/support/mock-api.ts`) implements the same rule. So refreshes must be single-flight (concurrent 401s wait for one refresh) **and coordinated across browser tabs** (e.g. Web Locks API or BroadcastChannel, with the tokens in shared storage). Two tabs refreshing with the same token sign the user out.
- **Media URLs**: every track has a `streamUrl` (valid 6 hours), FLAC tracks also an `opusStreamUrl` (the same audio as Opus in Ogg, about a quarter of the size; the first request for a track waits a few seconds for the conversion, unless it was converted ahead of time: `POST /api/transcodes` with `{device, tracks}`, at most 20 track ids, next first, answers 202 at once and converts them in the background; each request replaces the previous one of the same device, `[]` cancels it; `null` for MP3) and every album a `coverUrl` (or `null`; stable for a day, so the browser caches it). Both are signed and work without the Authorization header: use them directly as `<audio src>` / `<img src>`. Never build these URLs by hand and never put the JWT in a URL. When a `streamUrl` has expired (401), fetch the track again for a fresh one.
- Audio is served as is (FLAC or MP3) with HTTP Range support, so seeking works with a plain `<audio>` element. FLAC files are large (~30 MB per track).
- Lists include `hasLyrics`; the `lyrics` themselves only come with `GET /api/tracks/{id}`.
- Errors: a 401 from the authenticator is `{code, message}`; other API errors are JSON-LD `Error` objects with `status`, `title`, `detail`.
- There is no sign-up endpoint: accounts are created on the server with `docker compose exec php bin/console app:user:create <username>` (in `../Echora`).

## Local development

- CORS on the API allows `localhost` on any port in development, so the Vite dev server can call https://localhost directly.
- The API's HTTPS certificate is signed by Caddy's local authority. The browser must trust it, or `fetch` calls to the API fail before reaching it: open https://localhost/api once and accept the certificate, or import the authority from `docker compose cp php:/data/caddy/pki/authorities/local/root.crt <file>` (run in `../Echora`).
- API Platform publishes OpenAPI 3.2, and `openapi-typescript` 7 handles it (the 3.0.0 variant, `?spec_version=3.0.0`, yields the same types). `bun run api:types` runs on Node, which doesn't trust Caddy's certificate: run it as `NODE_EXTRA_CA_CERTS=<exported root.crt> bun run api:types`.
- The editor is Code - OSS with extensions from Open VSX: only recommend extensions published there.
